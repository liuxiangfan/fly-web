## 推荐实施顺序

### 第一批：正确性与异常安全

- SW-01、SW-02、SW-04 可分别实施；同时为 SW-03 和 SW-05 写失败反例。
- SW-03 必须按 SW-04 的字段契约提交，不继续依赖不完整的配置回滚。
- 先固定结果与现场行为，再谈优化速度；不新增算法、控制项或教学页。

### 第二批：可信验收与交互性能

- SW-06 先定义报告契约，SW-07 再依赖该契约登记跨平台结果。
- SW-08 补充长稳盲区，SW-10 修主线程取消。
- 本地先短轮验证量具，再投入长稳；所有失败记录保留，不能只留最后一份绿灯。

### 第三批：性能、体验与收敛

- SW-09 实测减重与交互性能；SW-11 完成可访问性矩阵。
- SW-12 逐职责迁移主文件，保留共享数值内核与既有教学行为。
- 最后冻结一个构建，完成完整门禁、跨平台稳定性、两份长稳和视觉复核。

## CI与执行授权边界

本次文档整理不提交、不推送、不触发远端任务。未来执行 SW-07 时：

1. 先获得授权，审阅需要提交的文件并提交改动，记录实际 SHA；不能只从 dirty 工作树建分支后直接 push，后者不会上传未提交代码。
2. 本地短轮通过后再运行已包含该提交的 workflow；确认五轮参数、两个平台、两片清单都真实执行。
3. 强化登记脚本后才登记 run/job/attempt 与报告 artifact；`current=true` 不得绕过来源检查。
4. 超时先记录为未完成或根因未知；没有诊断证据时，不把它直接归结为运行环境容量。

## 结案规则

每项至少提交：**错误输入／旧行为 → 生产修复 → 红到绿永久反例 → 定向输出 → 完整门禁 → 构建与证据身份 → 未覆盖边界**。

填表模板与可直接执行的本地验证顺序见 [实施方案第15～16节](SOFTWARE-IMPROVEMENT-PLAN.md)。

只写计划、只调分数、只通过计数检查或只补一条 CI 记录，均不能把工单改成已完成。
