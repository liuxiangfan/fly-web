## 2026-11-06 · v0.2.0 修复与发布准备

- 以真实 Windows CI 的两项断言失败为起点，不把完整执行后的交互响应和复制反馈失败归为纯容量问题。
- runner 异步调度保留步数硬上限，增加 4 ms 墙钟计算片预算；积分、种子与算法顺序不变，停止时点与指标收尾／Promise 返回时点分开记录。
- 交互测量采用至少 40 个 timer 样本和真实输入事件，固定 200 ms 目标；保留计算片、渲染、UI、长任务和取消时序的原始诊断，不按空闲基线放宽门槛。
- 公式正文与按钮分离；剪贴板 API 缺失、同步异常、拒绝、挂起有界回退；真实建立选区才提示按 Ctrl+C，迟到完成不改新操作反馈。新增 17 项确定性契约。
- 浏览器公式检查打开可见数学页并前置焦点，用真实点击和目标状态等待替代固定 300 ms；核对正文载荷与选区不含按钮文案。
- 为守住既有主包预算，复用重复的遥测模板、校准深拷贝与 Blob 下载路径；不删除教学功能或放宽预算。
- 中英文 README 同步 Windows 环境、复制回退、版本和真实 CI／部署关系；Release 的正式发布与验证结果将在完成后另记。

**正确性与异常安全（SW-01～SW-05）**

- **时间单位不再被启发式覆盖**（SW-01）：显式 `t_ms`/`t_us` 照声明换算；**没有声明单位时保留秒**，
  并在提示里给出可操作建议（"把表头写成 t_ms"），不再用"中位 dt>0.5 就除以 1000"猜单位；
  `monotonicTimelineMs()` 成为时间轴唯一来源（播放器与报告共用）。
- **Madgwick 遥测只报修正项**（SW-02）：零观测修正时 `correction=0`、`rate=gyro`，非水平单位姿态同样成立。
- **档案导入成为严格事务**（SW-03）：prepare（三份纯计划：控件/开关/校准）→ commit（渲染 → 读回 → 失败回滚）；
  渲染阶段抛异常时现场**一个字节都不动**。滑块量化改为"落在范围内的合法网格上"（旧实现会把越界值夹到
  不在网格上的最大值，导致离线模型与真实控件读回不一致）。
- **schema／克隆／规范化／校验同一份白名单**（SW-04）：未知 `estimators.<id>` 与 `params.<key>` 明确拒绝并给字段路径；
  克隆只从默认配置派生键集，规范形幂等（省略可选字段与显式默认值导出逐字节一致）。
- **超时、迟到完成与所有权**（SW-05）：原始操作（open/GATT/订阅）超时后句柄进隔离队列，
  迟到落定自行关闭；`dispose()` 只在真正关闭后返回 true；通知会话的"待结算停止"不再干扰新订阅。

**验收可信度（SW-06～SW-08）**

## 2026-11-03 · 纯软件满分轮（P0/P1/P2 全清）

- **P1 量具自身的两个缺陷（稳定性轮实测暴露）**：
  ① 长稳堆判据原先只看「首→末」两个采样，而 `usedJSHeapSize` 是 GC 锯齿波——三次 600 s 的
  端点差分别是 +15.5 / +14.9 / **+25.0 MB**（上限 24），第三次只是恰好起点在波谷、在波峰（那次
  常驻水位只升了 3.5 MB）。门禁因此变成"掷骰子"。现在改为比较**首尾窗口各自的最低点**（GC 后水位）
  并同时报告端点差，峰值与线性趋势照旧——锯齿相位不再影响判定，真泄漏仍然跑不掉。
  ② 「串口断线自动重连」用固定 600 ms 窗口数帧（`delta > 5`），机器忙时会数到 3 帧而误报失败
  （5 轮里出现过 1 次）。改为**状态等待**（等到真的超过 5 帧，最多 8 s）——与项目既有的"固定 sleep
  改状态等待"同一条原则。
- **P1 证据的源码绑定范围**：`sourceDigest` 收敛为**产品构建输入**（src/、public/、index.html、

  `statuscheck` 计数与 `budget-contract` 守住；把量具算进摘要会让"修一个 flaky 断言"也要求重跑
  二十分钟长稳（实测三次），反而逼人不敢改量具。`--require-source` 只对**由脚本对产品跑出来**
  的证据类型（长稳、稳定性、视觉）要求摘要一致；真机探针/线上 smoke/复算基准不做源码绑定（范畴错误）。
- **P2 CI 失败归因**：新增 `scripts/smoke-verdict.mjs`，`ci-run-smoke.mjs` 的摘要现在写
  `verdict: pass | product | capacity` 并逐轮打印归因行。判据保守：**出现任何用例级 `[FAIL] <用例名>`

- **BLE 接入轮**（2026-10-28，用户追问「Web Bluetooth 要做什么、为什么不做」——**我原先的理由只对了一半**）：
  - 我当初写「有意不做，理由：无法配对/验证任何 BLE 设备」。这句话对的部分：真机配对、厂商 UUID 组合、
  特定模块的 MTU 行为都无法在这里验证。**错的部分：应用侧整条链路完全可以验证**——就像假 Web Serial 端口
  那样，用一个假 GATT 服务就能在真浏览器里跑通全流程。我把「无法验证真机」错当成了「无法验证功能」，
  于是把一项可做的工作划掉了。记录在此，避免下次再犯同样的推理错误。
  - 实现（`main.ts` 的 BLE 段 + 面板控件）：
    · **只预置已核实的服务 UUID**：FFE0（HM-10/CC2541 透传）、Nordic UART（6e400001…，UUID 取自 Zephyr 的
      `nus.h`）、ABF0（SpeedyBee 类）、通用 1000 系列——后三组与 FFE0 的用法取自 iNav Configurator
      （FPV 圈最主流的 BLE 串口工具）的 `connectionBle.js`；另给「自定义」输入框。**不写死任何猜来的 UUID**。
    · **特征不预置**：连上后枚举该服务下所有 `properties.notify/indicate` 的特征列给用户挑，只有一个时自动订阅。
      原因：TX/RX 的命名方向各家不一致（Nordic 官方与 iNav 的 read/write 恰好相反），
      与其猜方向不如用客观属性。
    · **下游完全复用**：通知字节进同一个 `serialState.buffer/text` 再走 `serialDrainBuffer()`，
      于是三协议、安装方向、磁校准、无真值语义全部照旧；`state.real` 加上 `bleState.connected`，
      `dataSourceLabel()` 多一档「BLE IMU」，三条数据通路（串口 / BLE / 回放）互斥。
  - **BLE 的关键性质**：默认 ATT MTU 23 → 单个通知最多 20 字节，**28 字节的二进制帧必然分两条通知**。
    装置的流式解析器（不完整时 consumed=0、缓冲继续攒）天然重组，所以这一层不需要任何额外代码——
    但必须有用例守着。冒烟里用假 GATT 设备**故意按 20 字节分片**发 28 字节帧，断言重组后的读数正确
    （accel [0,0,9.8] / gyro [1.5,0,0]）；文本协议也走同一条通路验证一遍。
  - 踩坑：冒烟里最初等「时钟推进」来判断数据到达——而连接时会 `resetSim()` 把时钟清零，
    于是等待条件被**连接前的时钟**满足了（读到 `lastImu === null`）。改成等状态行出现非零帧率。
    这条记住：**验证数据通路要盯数据本身，不要盯派生的时钟**。
